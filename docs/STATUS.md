## Next engineering
- Migration placement, decided for the first deploy: `alembic upgrade head` stays in the start command. Render's pre-deploy command is not available on Free web services, and whether the build environment can reach the Supabase pooler is unverified. The first deploy log decides whether to move it to the end of `buildCommand`. The proposal below is kept for that decision; nothing was changed.
  - Migration placement (proposal, nothing changed). Today the start command is `alembic upgrade head && gunicorn ...`, so every cold wake-up of a Free service re-runs alembic (about 16.5 s of the boot at 0.1 CPU) before the port opens. Render's pre-deploy command, which would run it once per deploy, is not available on Free. Proposal: move `alembic upgrade head` to the end of `buildCommand` (after `python -m scripts.download_model`) and make `startCommand` just `gunicorn -c gunicorn.conf.py wsgi:app`. A failed build keeps the previous version serving, as a failed pre-deploy would. Needs checking first: that `DATABASE_URL` (a `sync: false` secret) and the Render Key Value URL are present in the build environment, and that the build environment can reach the Supabase session pooler (undocumented; the first deploy log answers it). Costs: the old code keeps serving against the migrated schema until the new build goes live, so migrations must stay backward compatible; `docs/deploy_phase3.md` ("Database migrations on deploy") and the "one instance" rule need rewording. If the build cannot reach Supabase, keep it in the start command and accept the 16 s, or move to a paid plan and use `preDeployCommand`.
- `follow-redirects` is fixed (1.16.1, lockfile only, 2026-10-22): `npm audit --omit=dev` 1 high to 0; full audit 8 to 7 (the Tailwind 3 chain, whose fix is Tailwind 4, a major bump). `npm ci`, `npx tsc --noEmit` and `npm run build` pass after it. Still unconfirmed: whether the vulnerable code was ever reachable from the browser build.
- Startup design proposal, awaiting approval, not implemented, not to be built before Render numbers exist. Problem: with `preload_app = True` gunicorn listens only after the imports and the app finish (about 80 s of imports at 0.1 CPU), so Render's port detection and health check see nothing meanwhile. Design: gunicorn binds at once with `preload_app = False` (no memory cost with one worker, per deploy_phase3.md); `wsgi:app` is a thin WSGI callable that answers the liveness route immediately while one background thread runs the imports, `create_app` and the model load. If that thread fails the process exits non-zero, so a missing model still fails the deploy loudly (today's `_require_embedding_model` guarantee). `/health/ready` reports `model_loaded: false` while it runs. Two options for requests that arrive before it is ready:
  - **A (recommended first):** every route except liveness answers 503 with `Retry-After` and a stable error code such as `starting`. One check in one place, so no route can score without the model. Cost: login and browsing are also unavailable until ready.
  - **B:** routes that do not need the model (login, listing) work once the app object exists; scoring and upload paths raise a `ModelNotReady` error that one handler maps to 503. Better first visit, but `create_app` would have to build the app before the model, and any path that today degrades to "no semantic score" when the model is unavailable would have to raise instead, or scores would silently lose their 40 % semantic part.
  Not measured: how quickly the port would open (expected seconds, because only Python, gunicorn and the thin callable load first), and whether the loading thread's GIL use slows liveness answers at 0.1 CPU. An alternative that attacks the cause: a lighter embedding runtime (Phase 4b audit), since `import sentence_transformers` alone is about 55 s here.
