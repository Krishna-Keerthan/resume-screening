# Stack

Every dependency has exactly one job (CLAUDE.md, Dependency policy). One row per technology:
its single job, where it is used, what it overlaps with, and the verdict. Adding a
dependency needs its row here first.

The full inventory of the existing dependencies is a Phase 4b task. Until then this file
lists the dependencies changed since Phase 3 began.

| Technology | Single job | Used in | Overlaps with | Verdict |
|---|---|---|---|---|
| `httpx` 0.28.1 | Synchronous HTTP client. Groq's SDK already uses it; the Supabase Storage backend calls the Storage REST API through it. | `app/services/storage_service.py` (Supabase backend); `groq` (indirectly) | `requests` (installed only because `huggingface-hub` needs it) and the `urllib` calls in the old Cloudinary download. Neither is used by app code for HTTP any more. | **Keep.** Declared as a direct dependency in `requirements.in` at the version the lock already held, so nothing new is installed. |
| Supabase Storage (a service, not a package) | Résumé file storage in a private bucket: random keys, signed download URLs that expire after 300 s, delete. Called through its REST API with `httpx`. | `app/services/storage_service.py` (`SupabaseStorageBackend`, chosen by `STORAGE_PROVIDER=supabase`); `scripts/supabase_smoke_test.py` | The local-disk backend (development and tests only; Render's disk is wiped on every deploy). Replaces Cloudinary. | **Keep.** Needs `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_BUCKET`; see `docs/deploy_phase3.md`. |
| `supabase` / `storage3` client libraries | Would wrap the same REST calls. | not used | `httpx` | **Not added.** Compared with REST-via-`httpx`: `supabase` adds 13 packages and about +4 to +6 MB RSS, `storage3` adds 8 packages and about +2 to +5 MB, `httpx` adds none. The 4 to 6 MB and 2 to 5 MB figures are RSS differences and stay valid. The earlier "9 MB of headroom" compared PSS (500 to 513 MB after 8 scorings under WSL) with the 512 MB limit; PSS includes file-backed pages (the model and libraries) that the kernel can drop, so it overstates what the OOM killer sees. What a cgroup limit counts as unreclaimable is anonymous memory: 297 MiB after boot in a 512 MB, 0.5 CPU container (`memory.stat`, no scoring yet; about 351 MiB after scorings in earlier runs, not re-measured), with no OOM kill. Render's own accounting is not measured; compare Render's memory graph, not PSS. |
| `cloudinary` 1.46.3 | Résumé file storage (authenticated raw uploads, signed URLs). | was `app/services/storage_service.py` | Supabase Storage (replaced it) | **Removed.** No code, setting or file refers to it; see the removal commit for the proof. |
| Supabase Postgres (a service, not a package) | The production database, reached through Supabase's **session pooler** (port 5432; `DB_SSLMODE=require`). | `DATABASE_URL`; `config/settings.py`; `migrations/env.py` (Alembic) | Render's Postgres, which `render.yaml` no longer declares. Supabase Auth, Data API and Realtime are not used: the app has its own JWT login. | **Keep.** Port 6543 (transaction mode, no prepared statements) is refused at startup. See `docs/deploy_phase3.md`, "Database on Supabase". |
| Render Postgres (a service) | Was the production database. | was `render.yaml` (`ats-postgres`, `fromDatabase`) | Supabase Postgres (replaces it) | **Removed.** Nothing in `render.yaml` or the docs refers to it as current. |
