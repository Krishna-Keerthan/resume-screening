# Database migrations (Alembic)

Run every command from `backend/`. The database URL comes from the app config,
so set `DATABASE_URL` (and `APP_ENV`, plus `SECRET_KEY` when `APP_ENV=production`).

```bash
alembic upgrade head        # apply all migrations
alembic downgrade -1        # undo the latest one
alembic current             # show the revision the database is at
alembic revision --autogenerate --rev-id 0003 -m "short description"
```

Always read an autogenerated migration before committing it.

## Revisions

| Revision | What it does |
|----------|--------------|
| 0001 | Initial schema: the models as of the Phase 2 repair. |
| 0002 | `recruiters.is_deleted` (NOT NULL, default false), `recruiters.deleted_at`, index `ix_recruiters_is_deleted`. |
| 0003 | Lowercases and trims every candidate and recruiter email, then adds unique indexes `uq_candidates_email_lower` and `uq_recruiters_email_lower` on `lower(email)`. Refuses to run, listing the rows, if two emails collide once normalised. The downgrade drops the indexes only; the email update is not reversed. Data paths: `migrations/verify_0003.sh`. |

## Production

Production starts from an **empty database** and is built only by migrations:

```bash
alembic upgrade head
```

The start command in `render.yaml` and the `Procfile` runs it on every deploy,
before gunicorn: `alembic upgrade head && gunicorn ...`. If a migration fails,
gunicorn never starts and the deploy fails, so the previous version keeps
serving. Production never calls `db.create_all()` (`CREATE_TABLES_ON_STARTUP`
is false there); development and tests still do.

On the first deploy the database is empty, so `upgrade head` runs 0001, 0002
and 0003 in order and creates `alembic_version` at `0003`. Later deploys with
nothing new do nothing. It needs `SECRET_KEY`, `DATABASE_URL` and a shared
`RATE_LIMIT_STORAGE_URL` in the environment, because Alembic builds the
production config the same way the app does.

Run one instance per deploy: if the service is scaled to several instances,
each one runs the command and they would race on the first deploy.

Do not `alembic stamp` production: there is no pre-existing data to preserve.

## Checking migration 0003's data paths

`migrations/verify_0003.sh` seeds a throwaway PostgreSQL database and checks that the upgrade
refuses a duplicate pair, normalises the emails once the duplicate is gone, that the unique index
rejects a case variant, and that `alembic check` is clean. It wipes the database it points at; see
the header for usage.
